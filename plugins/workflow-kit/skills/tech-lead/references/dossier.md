# Dossier

The dossier is the source of truth for one lead. It lives in the project's Obsidian vault.

## Layout

```text
<vault>/Features/
  _project/decisions.md      append-only, project-wide
  <feature>/brief.md         goal, constraints, architecture, non-goals
  <feature>/decisions.md     append-only, feature
  <feature>/log.md           append-only, one short entry per session
  <feature>/board.md         GENERATED by dossier.py board; never hand-edited
  <feature>/items/<slug>.md  one file per work item (frontmatter + notes)
  <feature>/designs/         stage 2 design notes
  <feature>/plans/           stage 3 handoff plans
<vault>/.gitattributes       contains `decisions.md merge=union` and `log.md merge=union`
```

There is no escalation file.

## File templates

`brief.md` has these headings:

```markdown
# <feature>

## Goal

## Constraints

## Architecture

## Non-goals
```

Each `decisions.md` entry is one append-only line:

```text
- <date> [<scope>] <decision> — <why> (<source>)
```

`<source>` is, for example, `design review`, `PR #52 unplanned`, or `user reversal`.

## Item format

Item frontmatter is a restricted YAML subset parsed and written without a YAML dependency.
The supported forms are `key: scalar`, `key: [a, b]`, and an empty value. The body after the
closing `---` is free-form Markdown.

| Key | Values |
|---|---|
| `slug`, `title` | text |
| `stage` | `idea` · `design` · `plan` · `implement` · `pr` · `review` · `merged` · `done` · `dropped` |
| `status` | `none` · `queued` · `blocked` · `running` · `paused` · `stuck` · `idle` |
| `origin` | `implement-plan` · `external` (a PR that was not opened by implement-plan) |
| `worker`, `sessionId`, `workerKind` | session name, id, and `plan`·`implement`·`ci`·`sync`·`comments` |
| `worktree`, `branch`, `pr`, `plan`, `design` | paths, branch, PR number, and vault-relative links |
| `blockedBy` | list of `<slug>` or `<feature>/<slug>` |
| `files`, `modules` | lists, from the plan |
| `notified` | list of event keys already sent, for example `pr-ready`, `fix-pushed-2` |
| `round`, `reviewSeen` | review-round counter, ISO time of the last review handled |
| `question` | one-line `Question:` from a stuck worker's `needs input` block, while `status: paused` |
| `unplanned` | count of `### Unplanned Decisions` items in the PR body; `0` for none |
| `updated` | ISO time, set on every write |

## Worker names

A worker is named `<feature>-<slug>`, plus `-<workerKind>` for every kind except
`implement`. Examples are `kmp-ktor` and `kmp-ktor-ci`. Notifications use the same name in
`claude attach <name>`.
`herdr.py` lowercases the worker name, replaces characters outside `[a-z0-9_-]` with
`-`, ensures it starts with a letter, and caps it at 32 characters. Long names keep the
last hyphen-separated part (the kind suffix when there is one) when it is 23 characters
or fewer, and get a 6-character stable hash. The tab label is the item title.

## Events

Every notification is one line under 200 characters and starts with `[<feature>]`.

Notify for: `plan-done`, `impl-started`, `pr-ready`, `fix-pushed-<round>`, `paused-<id>` (a
worker's `needs input`), `decision-<n>` (a lead-side ask), `stuck`, and `quota-blocked`.

Log only in `log.md`, without a notification: `phase-done`, `ci-fixed`, `synced`, and
`retro-ready`.

## Command contract

Every successful command writes exactly one JSON object to stdout and exits 0. Invalid usage,
unknown item keys, and invalid stages or statuses write an error to stderr and exit 2.
`herdr.py` also uses stderr and exit 2 for usage errors (including malformed items or a
missing worker for attach); mirror runtime failures return JSON `warning` with exit 0.

- `resolve-vault [--project-dir D]` → `{vault, source, featuresDir}`. `source` is `config`,
  `convention`, or `none`.
- `config [--project-dir D]` → `{maxWorkers, vault, herdr}`. `herdr` is a boolean from
  `lead.herdr`, default `true`; a non-boolean falls back to `true` and adds
  `warnings: ["lead.herdr must be a boolean; using true"]`, with exit 0. The `warnings`
  key is absent when there is no warning.
- `list --vault V [--match NAME]` → `{features}` and, when matching, `{match, closest}`.
  Each feature has `name`, total `items`, and `stages` counts.
- `init --vault V --feature F` → `{ok, featureDir, created}`.
- `item new --feature-dir D --slug S --title T [--set k=v]...`, `item get <file>`, and
  `item set <file> k=v... [--add k=v] [--note TEXT]` → `{file, item, body}`. `--set` may be
  repeated for `item new`; `--add` may be repeated for `item set`.
- `board --feature-dir D` → `{ok, board, changed, items}`. It emits a table for every stage,
  in the stage order documented above, with Item, Status, PR, Worker, and Updated columns.
- `sync --vault V -m MSG [--board D]... [--] [paths...]` → `{ok, committed, attempts}` on
  success; failure has `ok:false` and either `conflict` or `error`. A rejected push is retried
  up to three total attempts. A non-board rebase conflict is aborted before return.
- `checks [--project-dir D]` → `{allowRule, trusted, permissionMode, fixes}`.

`resolve-vault` and `config` merge `lead` keys from user then project
`.claude/workflow-kit.json`, so project keys override the same user keys. The vault convention
is `~/Workspace/Obsidian/<lowercased repo directory name>-vault`. `sync` never force-pushes;
only the lead passes `--board`, while workers never regenerate boards.
